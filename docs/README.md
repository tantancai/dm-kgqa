## 研发流程

每个版本（V1 → V2a → V2b → V3）都走一遍第 2～7 步，在上一版文档的基础上增量修改，不重写。

| 阶段 | 做什么 | 产出文档 | 对应毕设节点 |
|---|---|---|---|
| 1. 立项 | 为谁解决什么问题、值不值得做 | [立项说明](01-product/立项说明.md) | 开题报告 |
| 2. 需求分析 | 用户、场景、功能、性能与安全要求 | [PRD](01-product/PRD.md) | 开题报告 |
| 3. 概要设计 | 系统分几块、怎么协作、技术选型 | [架构设计](02-design/architecture.md)、[ADR](02-design/adr/) | 论文"系统设计"章 |
| 4. 详细设计 | 接口、数据结构、关键算法 | [接口契约](../contracts/openapi.yaml)、数据设计 | 论文"详细设计"章 |
| 5. 开发 | 按版本、按任务写代码 | 提交记录（带任务号）/ 子阶段 PR | 中期检查 |
| 6. 测试 | 功能测试、评测、压测 | [测试计划](03-test/test-plan.md)、测试报告 | 论文"实验"章 |
| 7. 发布 | 打版本、部署、交付使用 | 部署文档、[CHANGELOG](../CHANGELOG.md) | 答辩演示 |
| 8. 运营与迭代 | 收集反馈、修问题、规划下一版 | 用户试用记录，再回到第 2 步 | 论文"总结与展望" |

## 追溯链

```
PRD 需求编号 REQ-xx → 设计书任务号（如 V1.1-T2）→ 提交信息（同时写任务号和 REQ-xx）→ 子阶段 PR → tag（2026-11-04 起不建 Issue、里程碑和标签，任务清单以设计书为准）
→ 提交记录 → 测试报告中的用例 → 版本 tag
```

"为什么这样设计"查 ADR，"为什么做这个功能"查 PRD 的需求编号，"什么时候、怎么改的"查 PR。

## 设计审核关卡

设计从大到小逐层展开，**上一层经负责人审核通过后，才能进入下一层**；没有已批准的设计书，不写代码。

| 关卡 | 审什么 | 文档 | 状态 |
|---|---|---|---|
| G1 总体设计 | 架构、模块划分、技术选型 | [architecture.md](02-design/architecture.md) + [ADR](02-design/adr/) | 已批准（2026-10-30） |
| G2 分期计划 | 每期做什么、完成标准、时间 | architecture.md 第二、三节 | 已批准（2026-10-30） |
| G3 每期开发设计书 | 模块设计、数据结构、关键流程、异常处理、任务拆分 | `02-design/iterations/<期次>-design.md` | V1 总设计已批准（2026-11-02）；分阶段设计待写 |
| G4 每期评测目标 | 指标、目标值、对照组 | 每期设计书中的"评测目标"章 | V1 已批准（2026-11-02） |
| G5 端到端测试 | 覆盖的用户路径、通过标准 | 每期设计书中的"端到端测试"章 | V1 用例清单已批准；步骤在分阶段设计中补全 |
| G6 App 前端设计 | 页面结构、交互流程、视觉原型（必须有可以直接看的原型） | 每期设计书中的"前端设计"章 + 原型 | 未开始 |

- 设计书文件头写明状态：草稿 → 待审 → **已批准**（附批准日期）。模板见 [iterations/README.md](02-design/iterations/README.md)。
- 开发中必须偏离已批准的设计时，先停下来说明偏离点和原因，经同意后改设计书，再继续开发。

## 提交审核项

**每一次 commit 和 push 都要先经负责人审核确认**，不允许自行提交，也不允许把多次改动攒到一起提交。提交前交出审核包：文件清单与 diff 摘要、下面 9 项的逐条自检结果、拟定的提交信息、测试输出原文。

| # | 审核项 | 检查内容 |
|---|---|---|
| 1 | 范围 | 只包含本次约定的改动；没有无关文件、调试代码、临时文件 |
| 2 | 设计一致 | 实现与已批准的设计书一致；有偏离的逐条列出并已获同意 |
| 3 | 追溯 | 提交信息带任务号和 REQ 编号；提交信息符合 Conventional Commits |
| 4 | 安全 | 没有密钥、`.env`、真实用户数据、未授权数据；`git diff --cached` 已检查敏感词 |
| 5 | 正确性 | 测试通过（附原始输出）；新增的逻辑有对应测试 |
| 6 | 接口契约 | 接口有变化时已同步 `openapi.yaml`，且向后兼容 |
| 7 | 文档同步 | PRD / 架构 / ADR / 测试计划 / CHANGELOG 中受影响的部分已更新 |
| 8 | 评测影响 | 改动问答链路或提示词时，附评测前后对比；没有影响的写明理由 |
| 9 | 体积与格式 | 没有不必要的大文件或二进制文件；格式化和静态检查通过 |

## 开发约定

**分支**：`main` 始终保持可运行。每个子阶段开一个分支（如 `feat/v1.1`），每完成设计书中的一个任务提交一次（每次都先交审核包），子阶段完成后开一个 PR 合并并打 tag。只改文档的提交可以用 `docs/...` 分支。
- 分支名：`feat/<issue号>-<简述>`、`fix/<issue号>-<简述>`、`docs/...`、`exp/...`（实验）

**提交信息**：[Conventional Commits](https://www.conventionalcommits.org/zh-hans/)
- `feat:` 新功能 · `fix:` 修复 · `docs:` 文档 · `test:` 测试/评测 · `refactor:` 重构 · `perf:` 性能 · `chore:` 杂项
- 示例：`feat(qa): Text2Cypher 报错后带错误信息重写一次 (#12, REQ-05)`

**PR**：一个人开发也走 PR，按模板填写任务号、需求编号、测试方式。改动涉及技术决定的，同一个 PR 里补 ADR。

**版本**：完成一个版本就打 tag（`v1.0`、`v2a`、`v2b`、`v3`），并在 GitHub Releases 附上 CHANGELOG 和测试报告链接。

**GitHub 设置**：
- Milestones：`V1`、`V2a`、`V2b`、`V3`
- Labels：`feature`、`bug`、`docs`、`experiment`、`P0`、`P1`、`P2`
- 仓库可见性：答辩前保持**私有**，答辩后再公开

**绝不提交**：`.env`、API Key、真实用户数据、未经授权的原始爬取数据。
