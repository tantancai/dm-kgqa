# ADR-0003：先用 Python 实现全部功能，V3 再把网关换成 Go

- 状态：已采纳
- 日期：2026-10-29
- 关联：REQ-17～REQ-22

## 背景

导师建议考虑大量不同优先级用户在高并发下的负载均衡。Go 在大量并发长连接的场景下更有优势，开发者也有 Go 后端实习经验；但 AI 相关的生态在 Python，且毕设要求每个阶段都稳妥可交付。

## 可选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全部用 Python | 一种语言，风险最小 | 企业规模下，长连接数和多核利用会成为瓶颈；Python 单进程才能保证全局优先级 |
| B. 一开始就用 Go 网关 + Python AI 服务 | 更接近生产架构 | 拿不到"为什么换语言"的对比数据；早期要同时调试两套技术栈 |
| C. 先全部用 Python，V3 再把网关换成 Go | 先保证可交付；换语言有数据支撑 | 多写一个 Python 网关（但它会作为对比基线保留下来） |

## 决定

选 C。

## 理由与代价

- 大模型请求一次持续 10～30 秒，同时在线的连接数 ≈ QPS × 持续时间，所以连接数会远高于普通接口。这才是 Go 的真实优势所在，而不是"Go 计算得更快"（瓶颈在模型调用）。
- 不做对比就直接用 Go，选型只能凭理论；先做 Python 版，再用同一个压测脚本对比，换语言就有了数据依据。
- 寒假前先用熟悉的 Python 跑通全流程，毕设保底更稳。
- 代价：Python 网关要单 worker 运行（优先级队列在进程内存里），这个限制在论文中如实说明，它本身也是 V3 的动机之一。
- 前提：遵守 ADR-0001 的进程边界，否则换 Go 的成本会翻倍。
